v2.38 - September 7, 2026 (Save to Google Drive was broken, in two ways)
  A colleague testing in Microsoft Edge reported: "Logging in works but I
  cannot save the file in a folder... the folder gets highlighted but the
  file is not saved. The picker window also stays open." Three symptoms,
  two faults, both mine.
  1) The picker was never closed. GD.pick resolved its promise when a
  folder was chosen but never called setVisible(false) or dispose() -
  the Google picker does not close itself. So the overlay stayed on
  screen and the app looked frozen. It now hides and disposes the picker
  on every path - picked, cancelled, and thrown - and is guarded against
  a callback firing twice.
  2) A browser prompt() was raised while that overlay was up. The file
  name was asked with prompt(), which Edge (and others) suppress while an
  overlay such as the picker is displayed. The call returned null, the
  next line was "if(!name) return", and OCM gave up in silence: no file,
  no message, picker still there. This also explains why Open from Drive
  worked for everyone while Save did not - only Save used a prompt.
  Every question the Drive flow asks is now asked by OCM itself, in an
  in-app dialog, BEFORE any picker opens. No browser prompt() or
  confirm() remains anywhere in the Drive path, including the "replace
  what is in this browser?" question on opening.
  3) Choosing a folder is no longer compulsory. The new dialog asks for
  the file name and offers two ways on: "Save to My Drive", which creates
  the file at the top level with no picker at all, and "Choose a folder",
  for departments that keep course files in one. Most people want the
  file saved, not a tour of their Drive.
  4) Cancelling the folder picker no longer ends the flow in silence - it
  offers to save to My Drive instead, which is what the person was trying
  to do. The picker's own title now reads "Click a folder once to select
  it, then press Select", because the Select button stays disabled until
  a folder is highlighted and two testers read that as a dead end.
  Also in this release: the Google Cloud API key's application
  restriction was removed (console change, not a code change). Restricting
  the key by HTTP referrer cannot work with the Picker, whose validation
  request originates inside Google's own frame rather than from our page;
  it happened to pass in Chrome and fail in Edge with "The API developer
  key is invalid". The key is still restricted to the Picker and Drive
  APIs, and the OAuth client is still restricted by origin, so no other
  site can obtain tokens in our name. See GOOGLE_DRIVE_SETUP.md.

v2.37 - September 5, 2026 (Google Drive, as a second place a file can live)
  1) File > Open from Google Drive... and Save to Google Drive as...
  A department can now keep its course files in a shared Drive folder
  and open them from any browser - including Firefox and Safari,
  which cannot save straight to a local file. Google's own picker is
  used, so files shared with the user and files on shared drives
  appear as they would in Drive itself. Once a Drive file is open it
  is the file of record: the chip reads "Drive: <name> . saved" and
  every change writes back to that file after a short pause, exactly
  as the local-file link behaves. A Drive link and a local-file link
  are exclusive; whichever was opened last wins.
  2) The default is still "no network calls". Nothing is fetched from
  Google until someone clicks a Drive item - the sign-in and picker
  scripts are injected at that moment, not on page load. The
  permission requested is drive.file, the narrowest Google offers:
  OCM can read and write only files the user picked or that OCM
  created, and cannot list or read the rest of the Drive. About, Data
  & Backup and the footer now say precisely that instead of "no data
  ever leaves your device", and a privacy.html accompanies the app.
  3) A colleague's save is caught, not overwritten. Before every
  write the file's version number on Drive is compared with the one
  this browser opened. If they differ the write stops, the chip turns
  red and reads "conflict", and the File menu offers the three honest
  ways out: keep mine and overwrite, load the Drive version instead,
  or save as a copy. This is the merge problem that Drive for Desktop
  silently turns into "conflicted copy" files - surfaced instead.
  4) Sign-in is remembered by link, not by token. After a reload the
  Drive file is still the file of record, the chip says "reconnect",
  edits are held as pending, and the first click signs in, checks
  whether the Drive file moved on meanwhile, asks if it did, and then
  flushes the pending edit. A token that expires mid-session is
  renewed once and the write retried.
  5) The offline copy cannot sign in. Google requires a real web
  origin, so on the file on disk the Drive item stays in the menu and
  explains this when clicked rather than disappearing. Setup gains a
  Google Drive card with a switch to hide the feature for an
  installation, and fields where an institution can substitute its
  own Google Cloud project (client ID, Picker key, project number);
  blanks keep the defaults, which belong to the author's project
  "obe-course-manager". Every Google call goes through one small
  adapter, so the whole flow - lazy loading, sign-in, picking, the
  version check, the conflict paths, reconnect, retry - is exercised
  by the test harness against a mock; only the live sign-in itself
  needs the hosted copy.

v2.36 - September 4, 2026 (Apply is the floor for a complex-problem claim)
  1) A new floor, enforced from both sides. WP1 speaks of a
  first-principles analytical approach and WP3 of modelling and
  originality: nothing is being solved at Remember or Understand. So
  a CO at C1 or C2 must not carry any WP, whatever PO it maps to. The
  prompt says so as rule 4f, the pre-OUTPUT self-check tests it, and
  the referee refuses such a line in red. Until now OCM checked only
  the converse - a C4+ outcome or question with no WP - so a C2 line
  claiming WP1 and WP3 passed with "no issues".
  EA is deliberately exempt. A complex engineering ACTIVITY can be
  comprehended without the outcome solving a complex problem, which
  is exactly what indicator 9a describes. The floor is about WP only.
  WP3 on a C3 outcome now draws an informational nudge: abstract
  thinking and originality usually sit at Evaluate or Create, and at
  Apply the reason should say why.
  2) The level rule is a departmental decision, not a software
  default. Setup - Defaults for New Courses, and the Version 2.2
  entry screen, now carry "Outcomes mapped to the complex-problem POs
  (PO1-PO6)": either keep the level as written and flag a C1/C2
  outcome for the committee, or require Apply (C3) and let the
  conversion raise it. The installation default is to keep.
  On "keep", the prompt is told not to raise a level - that changes
  what will be taught and assessed, and belongs to the committee -
  and to report the outcome as foundational with a note that the PO
  mapping may need review.
  On "require C3", the prompt raises a C1/C2 outcome mapped to
  PO1-PO6, rewrites it with an observable C3 verb that keeps the
  subject matter the teacher already covers, proposes WP1 with at
  least one more, and must open the Reason with "Level raised under
  departmental policy". It is told not to invent subject matter to
  justify the level: where the outcome cannot honestly be taught and
  assessed at C3 with the content it has, it keeps the level, claims
  no WP, and names the PO the outcome should be re-mapped to. An
  outcome raised on paper and examined at C2 is a Criterion 2
  weakness, which is Group A, and worse than an honest C2.
  A raise made under the policy is now an informational note naming
  the committee rather than a rule breach, and accepting the proposal
  carries the new level onto the Version 3 course, so the Bloom
  column, the verb alarm and the question-level checks all describe
  the same course. A raise the policy did not ask for - C4 to C6, say
  - is still warned as before. Every raised outcome still reaches the
  Specialization Committee on the CO Modification Request Form, which
  already prints the existing level beside the proposed one.
  3) A justified dash no longer looks like a defect. Under "keep", a
  CO mapped to PO1-PO6 with no WP whose Reason calls the outcome
  foundational now gets an informational note - the committee should
  satisfy itself that the later course named carries the
  complex-problem work - instead of the amber warning telling the
  writer to do what the Reason has already done. A dash with no such
  justification still draws the warning.

v2.35 - September 4, 2026 (four defects in the conversion prompt)
  1) Rule 8 was contradicting the opening. The prompt now begins by
  saying it proposes a claim and must not withhold an attribute for
  want of evidence - and then, as the last instruction before the
  self-check, rule 8 repeated the departmental minute that "WP/EA
  claims must rest on actual teaching and assessment evidence". The
  minute is right, but it is addressed to the teacher across the
  coming semester, not to a model at conversion time; leaving it bare
  gave the model a contradiction to resolve, and it resolved it
  conservatively. Rule 8 now carries the instruction and says whom it
  binds: a claim proposed here obliges the teacher to design
  assessment that evidences it, and OCM checks that afterwards.
  2) Rule 4 still offered an escape. It ended "propose WP1 and at
  least one of WP2-WP7, or propose none" - reopening the door that
  4b had just closed. It now reads: whenever you propose WP at all,
  propose WP1 together with at least one of WP2-WP7.
  3) The worked examples cited an indicator that did not exist. One
  example used PI 6f, which is in BAETE's suggested list but not in
  a set whose PO6 stops at 6c - so a course on ME_Type1 received a
  prompt teaching it to use a label the same prompt had just shown
  was unavailable. Example labels are now generated from whichever
  set is loaded. Two examples also predated rule 4b and left a dash
  in WP unexplained; both now justify it as the rule requires.
  4) The modern-tools heuristic was nominating WP3 by reflex. It read
  "evaluating or analysing with modern tools -> WP1 with WP3", and a
  real run duly proposed WP3 for an outcome that evaluates
  technologies with standard software. It now asks what the
  evaluation actually weighs - WP2 where factors compete, WP3 only
  where the choice has no obvious answer, WP4 where the technology is
  unfamiliar - and states that running a standard tool by a standard
  method is not by itself WP3.
  Noted for the record: inverting the default in v2.34 traded
  under-claiming for a mild pressure to over-claim, since a second WP
  must be found and WP3 is the most elastic of the seven. That trade
  is deliberate - an over-claim is visible on the printed outline and
  the committee can prune it, whereas an empty field told nobody
  anything - but no software check can catch it, and the course
  teacher remains the backstop.

v2.34 - September 4, 2026 (the prompt was asking the wrong question)
  1) The conversion prompt now says what it is for. A real run
  returned "WP: -" for three of five COs, with reasons of the form
  "no WP is proposed because ... its wording alone does not establish
  that assessment as a complex engineering problem without supporting
  assessment evidence". The model was not failing to reason: it was
  answering the question as asked. The prompt had invited it to
  decide whether a CO EVIDENCES a complex problem - a judgement that
  needs assessment items, rubrics and marks, none of which the prompt
  carries. The prompt now opens by stating what it is producing: the
  CLAIM each outcome will make under Version 3, which the teacher
  then designs assessment to match and which OCM audits later,
  question by question, in the CA and CQI Sections. Withholding an
  attribute for want of evidence is explicitly ruled out - that
  judgement belongs to a later stage and a different tool.
  2) The default is inverted. Rule 4b had permitted "-" for a
  foundational outcome and then added that an attribute the
  assessments cannot evidence "is worse than an honest gap" - a
  permission that was read as a preference, exactly as the PI dash
  had been before v2.29. For a CO mapped to PO1-PO6 the rule is now
  to propose WP1 and at least one of WP2-WP7; a dash is the
  exception, allowed only where the outcome is positively judged
  foundational at C1 or C2, and the Reason must say which kind of
  later course carries the complex-problem work. The "honest gap"
  sentence is gone; the WP1-plus-one rule and the referee already
  prevent invention.
  3) The prompt now gives the model something to reason with. From
  Table 6.2 and the outcome's own words: design, develop, formulate
  or optimise a system points to WP3 and usually WP7; weighing
  social, environmental, economic, ethical, legal or safety factors
  together points to WP2; selecting or siting for a context points to
  WP2 and often WP4; evaluating with modern tools points to WP1 with
  WP3; working across disciplines or with diverse stakeholders points
  to WP6; new or emerging technology to WP4; work beyond standards
  and codes to WP5 - with WP1 accompanying all of them because each
  requires in-depth knowledge at WK3-WK6 or WK8. A worked example
  shows a C5 outcome given WP1 and WP3 from its wording alone.
  4) Inherited attributes are treated as approved record. A course
  whose Version 2.2 outline claimed P1 and P7 had them carried across
  with the hedge "should be retained only if the design assessment
  evidences ...". They map positionally and are stated as fact; the
  committee prunes what it disagrees with, and the software checks
  the evidence afterwards.
  5) Two new checks. The prompt asks the model to verify its own
  lines before writing them - every PO1-PO6 outcome carrying either
  two WP numbers or an explicit foundational reason, every PO9
  outcome at least one EA, and no reason hedging an attribute it
  proposes. The referee adds an informational note where a reason
  says "only if" about an attribute the same line claims.

v2.33 - September 4, 2026 (the BAETE definitions, enforced)
  1) Ranges expand. Typing 1-7 in the Complex Problem Solving cell
  now selects all seven, and 1-5 in Complex Engineering Activities
  selects all five. A hyphen, an en dash, "to" or "through" all
  work, in every numeric cell - PO, Knowledge Profile, WP, EA and
  SDG - and lists and ranges mix freely (1, 3-5, 7). BAETE's own
  tables are written as ranges, so a teacher copying "WP1-WP7" from
  an outline meant all seven; until now it read as two.
  2) The complex-problem definition is enforced as written. Table
  6.2 of ACC-MAN-02 v3.0 defines a complex engineering problem as
  having "WP1 and some or all of WP2 to WP7". OCM treated WP1 as a
  gateway but accepted it alone; WP1 by itself is now refused in
  red, because depth of knowledge without any of the features that
  make a problem complex is not a complex problem. Table 6.3 sets no
  gateway - "some or all" of EA1-EA5 - so a single EA remains valid,
  and the prompt says so.
  3) Which POs expect what, from the PO statements themselves.
  PO1-PO6 are each written in terms of complex engineering problems;
  PO9 is the only PO written in terms of complex engineering
  activities; PO7, PO8, PO10, PO11 and PO12 mention neither. The
  conversion prompt states this, and the referee applies it in two
  tiers:
  - per CO, amber: a CO proposed for PO1-PO6 with no WP, or for PO9
    with no EA, is asked to justify itself as foundational in the
    Reason - a real and legitimate case, since complex-problem work
    may sit in later courses. WP claimed outside PO1-PO6, or EA
    outside PO9, is questioned the same way.
  - per course, red: a course that maps PO1-PO6 but has no outcome
    anywhere carrying WP1 with at least one of WP2-WP7 is making a
    complex-problem claim it cannot evidence; likewise a course
    mapping PO9 with no EA at all. Criterion 5.3(vi) is a programme-
    level demonstration, so the course-level test is the honest
    place for a hard stop.
  The prompt is explicit that an attribute the assessments cannot
  evidence is worse than an honest gap - the aim is not to fill
  every cell.
  4) The Knowledge Profile attributes cited in each PO statement -
  PO1 and PO2: WK1-WK4; PO3: WK5; PO4: WK8; PO5: WK2, WK6; PO6: WK1,
  WK5, WK7; PO7 and PO8: WK9; PO11: WK8 - now travel in the prompt
  as guidance, and a proposed WK set sharing nothing with the cited
  set raises an informational note.
  5) The CO table uses BAETE's own column names - Knowledge Profile,
  Range of Complex Problem Solving, Range of Complex Engineering
  Activities - each showing its range for the framework in force
  (WK1-WK9 / WP1-WP7 / EA1-EA5 under Version 3, K1-K8 / P1-P7 /
  A1-A5 under Version 2.2), and the framework selector is shortened
  to "Version 2.2 - to convert" and "Version 3 - already approved".

v2.32 - September 4, 2026 (complete Course Information before converting)
  1) The entry screen now carries every Course Information field.
  "Start from a Version 2.2 Course Outline" asked for five details;
  Course Info holds nine. Program, Section and Cohort were missing,
  so a converted course reached the Course Outline without its
  programme, and the Direct Calculations and CQI Report without the
  cohort - each then typed in again by hand. The screen now matches
  Course Info field for field, with the same labels: Course Code,
  Course Title, Credit Hours, Semester / Session, Program, Section,
  Cohort, Course Teacher(s), and the two choices this screen adds -
  which framework the outline follows, and which PO Indicator set
  the programme reports against.
  2) Building is blocked until they are filled. The button is
  disabled, and every empty field is named on screen as it is - not
  only when the button is pressed - beside any CO-row problems, in
  one list. Whitespace does not count as filled, and calling the
  build directly is refused with the same list.
  3) Section is the one exception, deliberately. A course with no
  sections leaves it blank, exactly as the Course Info screen
  allows, and the label says so. Where a section is given it prints
  with the course code as before.

v2.31 - September 4, 2026 (the grading policy as a table)
  1) Grading Policy is its own card in Setup, above Defaults for New
  Courses. It was a single free-text field tucked among the
  institution details; it is now a three-column table - Numerical
  Value, Letter Grade, Grade Point (GP) - shipped with the standard
  ten-grade scale: 80% and above A+ 4.00, down through 40% to less
  than 45% D 2.00, and Below 40% F 0.00.
  2) Every cell is editable and rows can be added or deleted, so a
  programme whose scale differs is not forced into this one. A
  "Restore the standard scale" button undoes any experiment.
  Deleting the last row leaves one blank row rather than silently
  restoring ten - the delete button now does what it says.
  3) The scale feeds two documents rather than sitting in a field.
  Course Outline section 15 prints the table itself, not a sentence.
  Course Report 4.1 takes its grade-distribution columns from the
  letters in the table, so a scale with an extra grade - or one
  short - is reported correctly instead of against a hard-coded
  A+ to F row.
  4) A course may still override the institutional scale with its
  own note in its Outline data; where it does, that note prints
  instead of the table, as before.
  Files saved earlier gain the standard table; a scale already typed
  into a course is untouched and still reads as an override.

v2.30 - September 4, 2026 (three placement fixes)
  1) The File control is a fixed landmark. Its button now always
  reads "File", with the file name and save status beside the word
  rather than replacing it - previously a linked file turned the
  control into "obe-course-data.json - saved", so a user looking for
  "File" could not see one. It is also present on browsers without
  the File System Access API, where it used to remove itself
  entirely; there it offers Export ALL Courses and Import JSON and
  says plainly that this browser keeps the data in the browser.
  Export and import are now in the menu in every state, alongside
  the file actions.
  2) "Start from a Version 2.2 Course Outline" joins the File menu.
  It is a way of opening a course, so it belongs where a user looks
  for one - available from every state of the menu, including on
  browsers that cannot link a file. It remains on the Welcome card
  and the Dashboard.
  3) The grading policy moves to Setup. A letter-grade scale is an
  institutional rule, not a per-course choice, and it sat in Course
  Info where every teacher retyped it. Setup now carries it, with the
  standard scale as the shipped default; the Course Outline prints
  the institutional scale unless a course has recorded its own, which
  it still may where a programme genuinely differs. Files saved
  earlier keep any scale already typed into a course - it simply
  reads as an override - and gain the institutional default for
  courses that had none.

v2.29 - September 4, 2026 (the PO Indicator rule, corrected)
  1) A dash in the PI field was the wrong answer, and the prompt
  invited it. Rule 6 had said to write "-" when no indicator fitted
  "the CO's Bloom level or content", and models duly refused
  indicators whose verb sat above the CO's level. Three of five COs in
  a real ME 4011 conversion came back with no indicator, including one
  - "evaluate selected renewable energy technologies using modern
  tools and techniques" against 5a "Select and apply appropriate
  experimental, computational and engineering techniques, resources
  and modern tools" - where the indicator plainly fits.
  The premise was mistaken. A PO Indicator states what the PROGRAMME
  expects of a graduate for that PO; a single course contributes a
  part of it. Requiring the indicator's verb to match the CO's Bloom
  level would mean no comprehension-level CO could ever be mapped to
  any PO, which contradicts a CO-PO mapping the department has already
  approved - and indicator ticks are documentary in any case, entering
  no attainment calculation.
  2) Rule 6 is inverted. Every proposed PO must now carry at least one
  indicator: the one the CO contributes to most, partial contributions
  included. The prompt states explicitly that the indicator's level
  need not match the CO's, gives the reductio above as the reason, and
  offers a worked illustration in which a C2 outcome is mapped to an
  analysis-level indicator because it builds the knowledge the
  analysis rests on. A dash is now permitted only where NO indicator
  of that PO is served at all - and it must then say that the PO
  mapping itself is unsupported and name the PO the CO really serves,
  with the indicator it would carry there. A third illustration models
  exactly that, redirecting a C1 knowledge outcome from PO6 to PO1.
  3) The referee follows. A proposed PO with no indicator is reported
  as an unsupported mapping rather than as a decision the teacher may
  take either way - the earlier wording, which invited them to "decide
  whether this CO supports the course without evidencing a PO
  Indicator", was itself part of the error. A PO that carries no
  indicator of its own, while another PO on the same CO does, is
  flagged separately.
  4) Candidate indicators are offered as chips. Under the pencil, each
  proposed PO lists its own indicators as clickable labels with the
  full text on hover, so correcting a missing indicator takes one
  click instead of another round trip to the AI. A note repeats that a
  partial contribution is enough.
  5) Accepting now guarantees the committee form. Accepting moves the
  teacher to the new Version 3 course, while the CO Modification
  Request Form prints from the Version 2.2 record; if the rows had not
  been drafted, they are drafted as part of accepting, and the
  confirmation says which record the form prints from.

v2.28 - September 4, 2026 (a reported gap, and the bug behind it)
  1) The measurable-verb alarm was blind to real wording. It stripped
  only "students will be able to" before looking at the opening verb,
  so a statement written the way outlines actually are - "After
  completion of the course, the students will be expected to
  comprehend the working principles ..." - passed silently. The alarm,
  the CQI outcome-quality findings and the conversion referee all
  depend on that one function, so all three were disabled on the
  statements teachers really write. Lead-ins are now removed in
  layers, longest first and repeatedly: after / at / by / on / upon
  the completion, conclusion or end of the course or semester; the
  students, learners, participants, candidates or graduates; will,
  shall, should, can, could, must, may; be expected / able /
  required; be able to, are able to, have the ability to; a leading
  "to"; and a leading adverb. Eight real phrasings now trip the
  alarm; four sound statements are left alone.
  2) The PO Indicator set is asked for, not assumed. Which set a
  programme reports against is a departmental fact, and a teacher
  converting a first course had no way to know OCM had quietly
  defaulted them to BAETE's suggested 46. The entry screen now asks
  it beside the framework question, shows each set with its indicator
  count, and says plainly that it is a departmental decision. The
  answer becomes the installation's default, so it is asked once and
  then remembered; the conversion card repeats it as a selector, so
  the set going into the prompt is visible at the moment it matters.
  It governs the record, the prompt, and the indicators ticked on the
  accepted Version 3 course.
  3) A dash in the PI field must now be explained. Rule 6 of the
  conversion prompt asked for "—" when no indicator fitted, and said
  nothing more; a Version 3 PO6 has no indicator at comprehension
  level, so a knowledge-level CO produced a bare dash with no
  explanation. The rule now requires the nearest indicator to be
  named and the mismatch explained in the Reason. The prompt's worked
  example, which had used exactly that ill-fitting pairing and so
  invited copying, is replaced by two clearly labelled illustrations
  - one where an indicator fits, one where none does.
  4) The referee flags an empty indicator field. An amber note names
  the proposed PO and the set in use, points to the Reason for the
  nearest indicator, and puts the question where it belongs: does
  this CO support the course without evidencing a PO Indicator, or
  should its level or mapping go back to the committee?

v2.27 - September 4, 2026 (the conversion, done the user-friendly way)
  1) The CO table replaces the two paste boxes. "Start from a
  Version 2.2 Course Outline" now opens one table - a row per CO,
  numbers only: PO (1-12), BT Domain (C/A/P) and BT Level, Knowledge
  Profile, Complex Problem Solving, Complex Engineering Activities,
  and SDG. Rows are typed in place and added or deleted freely, or
  the same columns are downloaded as a CSV template, filled in a
  spreadsheet and imported; the table can be exported at any point.
  Because every cell is a number, one question - "does this outline
  follow Version 2.2 or Version 3?" - is asked once and every cell is
  validated against it: PO out of 1-12, a level outside its domain's
  range (C 1-6, A 1-5, P 1-7), K9 or an SDG in a Version 2.2 file, an
  empty statement - each named by CO before the record is built,
  nothing dropped in silence. A Version 3 file becomes a Version 3
  course directly, with no conversion step, so a colleague holding an
  approved v3 outline uses the same door.
  2) An AI prompt does the conversion; OCM referees it. The v2.26
  worksheet - five text boxes per CO and a findings list - exposed the
  machinery and did nothing about the one thing that needs judgement,
  the wording. It is gone. In its place, three steps on one card:
  - Copy the conversion prompt. It carries the COs as recorded, the
    official Version 3 PO statements, the WK1-WK9 / WP1-WP7 / EA1-EA5
    descriptors, the programme's indicator set with its 1a-style
    labels, the SDG list, eight rules stated flatly (the PO7 trap, one
    PO per CO, positional K->WK with the widened four and WK9 as new,
    WP1 as gateway, rewrite unmeasurable verbs at the SAME level,
    indicators only from the set and only of the proposed PO, SDGs
    only on PO2/3/6 and only if teachable and assessable), the ME
    programme's decisions of 31 August 2026, and a strict one-line-
    per-CO output format. Run it in any AI tool - OCM makes no network
    call.
  - Paste the proposal back. OCM reads the lines (prose and markdown
    around them are ignored) and fills a review table: proposed
    statement, PO with indicators, WK/WP/EA, SDGs, reason. Each row
    has an Accept tick and an edit control.
  - The referee runs on every row, whether the AI wrote it or the
    teacher did: an unmeasurable verb; v2.2 PO7 proposed as v3 PO7;
    a departure from the published correspondence; no PO; WP without
    WP1; SDGs on a PO other than 2, 3 or 6, or more than three; an
    indicator not in the set, or belonging to a PO not proposed; a
    raised Bloom level; WK9 as an information note. Rows are tinted
    red or amber accordingly. Until a proposal is pasted, the table

v1 — July 13, 2026 (first release)
  Core:
  - Course management (multiple courses), Course Info, attainment settings.
  - COs with Bloom's taxonomy (C/A/P) and click-to-set CO-PO mapping matrix
    (12 Washington Accord Program Outcomes, strengths 1-3).
  - T&L Activities tab: CQI-aware recommender with a pool of 31 pedagogies
    (extensible with custom activities), per-CO recommendations filtered by
    mode and class size, one-click adoption into delivery methods.
  - Assessment plan: assessments with CO-tagged items and maximum marks.
  - Students & Marks: individual/bulk enrolment (Excel paste), marks grid,
    Empty Template (CSV) / Import Marks (CSV) / Export Marks (CSV).
  Attainment:
  - Direct measurement following the AUST "Direct CO-PO Calculations"
    workbook method (Target Pass Marks 40, KPI 50, per-student PO scores
    weighted by CO allocated marks), with charts.
  - Indirect measurement via CO Exit Survey (tally grid, Google Forms CSV
    import, printable survey form), Likert threshold configurable.
  - Combined attainment with user-editable Direct/Indirect weights
    (default 80/20).
  CQI (BAETE Criteria 3.8 & 5.4.3):
  - Auto-compiled per-CO table of T&L methods, assessment tools, CP/CEA;
    narrative fields (complex problems, effectiveness, tool design,
    question moderation).
  - Six-step CQI-loop status board; action tables two-way linked with
    Course Report 6.1 and Course Specifications 6.1.
  - Low Attainment Analysis linked to the Attainment tab: threshold filter
    for low-scoring students per CO, item-wise average diagnostics,
    analyses w.r.t. (a) T&L activities and (b) assessment techniques,
    and comments.
  - Stakeholder Feedback Register and Annexure H evidence checklist.
  AUST Documents (auto-filled, printable):
  - Course Outline, Course Specifications, Final Examination Vetting Form,
    Direct CO-PO Calculations, CO Exit Survey, Course Report, CQI Report.
  Data:
  - Work on a real .json file with auto-save (File System Access API,
    Chrome/Edge), reconnect flow; localStorage cache; JSON export/import;
    "Duplicate for New Semester (CQI)" carrying action plans forward.
  Documentation:
  - Faculty User Manual (docx) with Appendix A: T&L activity pool
    descriptions and selection justifications.
